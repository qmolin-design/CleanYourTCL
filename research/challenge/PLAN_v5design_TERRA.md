1. **高｜第 53、118、220 行｜重開機判斷不可靠**：開機後的 `elapsedRealtime` 若已超過上次存檔值，就不會被認作重開；可能扣掉跨重開機的錯誤時間，最多 180 秒。開機第一跳不扣也會漏掉斷電前最後一段，不能保證少扣 ≤1 分鐘。｜記錄可辨識重開的 boot ID 或開機次數，並測試「重開後 uptime 大於舊值」及斷電前後邊界。

2. **高｜第 52～60 行｜取樣扣額可被反覆繞過**：每跳只看當下前景，孩子可在每次取樣前切回桌面，其餘時間看 YouTube 而幾乎不扣；反過來也可能把剛切入之前的時間全扣掉。「平均抵銷」沒有依據。｜改用可驗證的前景切換事件或持續計時機制；至少實測反覆切換並明列可接受誤差。

3. **高｜第 53、169 行｜180 秒上限讓長時間故障變免費觀看**：鬧鐘延遲、程序凍結或 adb 等待 30 分鐘，恢復時最多只扣 3 分鐘；把上限改成歷史最大間隔也無法保證未來不超過。｜明訂超時後的保守處理和通知，驗收注入超長延遲，不能只依 19:00 樣本推論。

4. **高｜第 54、56、118 行｜「用完 10 秒內鎖定」缺乏保證**：短鬧鐘要等前一跳查 adb、存檔、網路連線與讀取結束才安排；單是網路連線及讀取各可等 10 秒，TCL 凍結或 adb 授權等待更久。｜先安排到期鬧鐘並與網路同步隔離，量測最壞延遲；達不到就調整驗收承諾。

5. **高｜第 71～75、196、222 行｜分頁的 `max_seq` 容易跳過加值**：最多回 100 筆，卻同時回整個資料庫的 `max_seq`；若電視把游標推到 `max_seq`，第 101 筆以後就白白漏領。｜一般同步只能確認「實際完整套用的最後一筆 seq」，用 101 筆以上及中途斷線測試；首次初始化則另訂明確規則。

6. **高｜第 73、250～253 行｜首次同步會吞掉家長的新加值**：全新安裝或清資料後、第一次同步前按下的加值，會被 `last_seq=null` 的初始化規則全部跳過；家長頁可能顯示已接收，電視卻沒拿到。｜先完成初始化並顯示可加值狀態，或明訂初始化基準及待領加值處理；驗收涵蓋先加值、後首次同步。

7. **高｜第 74、122 行｜D1 重建或還原會讓 seq 防重失效**：若新庫 seq 尚未追上舊 `last_seq`，會漏領；對齊後若舊資料被還原或編號重用，也可能重複領取。單靠數值比較無法識別資料庫世代。｜加資料庫世代識別，世代改變時停止自動套用並走明確復原流程；測試重建、還原及新舊 seq 重疊。

8. **高｜第 50、55、57 行｜加值與游標沒有完整的原子持久化規格**：套用額度後、保存 `last_seq` 前斷電，可能重複加值；反過來先存游標則可能少領。暫存檔 rename 也未指定寫入失敗、同步與掉電後如何處理。｜額度、游標及扣款狀態作為同一份完整狀態提交；在每個寫入與回應邊界注入失敗，確認只套用一次。

9. **高｜第 80、189～197 行｜家長加值請求沒有防重鍵**：Worker 已寫入但手機未收到回應時，重新按或重試會產生新 seq，額度加兩次；seq 自增只能防電視重領，不能防同一操作重建。｜每次家長操作帶唯一請求 ID，資料庫以唯一約束去重；測試回應遺失、雙擊及兩支手機同時操作。

10. **高｜第 59、147～161、259 行｜切換與回滾會互相打架**：歸零後沒有等待電視確認，接著停 v4 並開 v5，可能沿用影子額度而開放；回滾時 KICK 也未確認 `enforce=false` 就啟動 v4，v5 可能繼續啟用、v4 又停用。｜每一步先確認同步游標、實際設定與 YouTube 狀態，再進下一步；失敗時停在已知安全狀態。

11. **高｜第 117、157、211、216 行｜緊急回滾依賴可能已失效的 Mac adb**：關 USB 偵錯、撤銷授權或 adbd 故障時，Mac 也可能無法推設定與復原；覆寫設定檔若中斷，還會觸發「不存在／無效時不控管」。｜先保護既有 Mac 金鑰、確認連線與設定完整寫入；另列電視端可操作的復原方式及無 adb 時的限制。

12. **高｜第 129～136、211～215 行｜強制停止後未必能自動復活**：若管理員擋不住，App 停在 YouTube 已啟用的狀態，鬧鐘也不能當成可靠自救；Android 文件說明強制停止會移除相關執行狀態，須明確啟動元件才脫離停止狀態。｜把防護效果列為 TCL 實測前置條件，測停止後鬧鐘、重開及 KICK；若擋不住，明示可能持續開放。([developer.android.com](https://developer.android.com/reference/android/content/Intent?utm_source=openai))

13. **高｜第 100、105、129、132、135 行｜失聯通知有明顯盲點**：最後一次回報是 `screen=off`，孩子之後開機、停用 App、斷網或恢復原廠，就不會通知；「最後一筆一定開著」不成立。｜先實測待機回報，再決定不分螢幕偵測失聯，或明確接受盲點；測「待機→開機→立即斷線」。

14. **高｜第 104、197 行｜通知失敗後可能永久漏報**：若先把警報標成已通知，ntfy 請求失敗就不再重試；同時只記 `notify-fail`，家長可能看不到。兩個併發 cron／同步也可能重複推播。｜區分「事件發生」與「通知成功」，以原子狀態更新和有限重試處理；驗收非 2xx、逾時、併發與恢復。

15. **高｜第 131、144、214～215、268～271 行｜裝置管理員的防護與通知是假設，卻不是上線門檻**：清資料、強制停止是否被擋尚未實測；`onDisabled` 能否及時啟動及連網也未證實，且每次程序啟動又自動設管理員，行為可能衝突。｜先在影子期逐項實測並訂失敗處置；若保留管理員，明確定義停用後是否自動重啟用與通知時序。

16. **高｜第 137、234、269 行；需求第 55～69 行｜只停原生 YouTube，不能推論其他入口都被擋住**：瀏覽器、YouTube Kids、第三方播放器與投放接收途徑沒有完整測試；工單又禁止控制其他套件。｜逐項實測並列可繞過清單，請 Owner 接受範圍；禁止以 T 鍵、語音通過就宣稱整體封鎖。

17. **中｜第 84、193～194、243 行｜JWT 驗證測試不完整**：未明列固定 `alg=RS256`、依 `kid` 選可信公鑰、未知 `kid` 重新取鍵、異常 JWKS 與快取輪替；一小時快取可能讓合法請求在換鍵後失敗。`common_name` 對應 Client ID 的設計有官方依據，**確定程度高**。｜補換鍵、錯誤演算法、未知 `kid`、錯誤 issuer 及家長／電視身分交叉測試。([developers.cloudflare.com](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/?utm_source=openai))

18. **中｜第 123、192、239～240 行｜service token 缺到期與更新流程**：token 洩漏之外，正常到期或被停用也會讓同步與通知失效；官方 API 文件列出的預設期限為一年，**確定程度高**。｜部署時記錄到期日、設提醒，寫明更換及驗證步驟，並測 Access 401／403。([developers.cloudflare.com](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/service_tokens/?utm_source=openai))

19. **中｜第 32、75、89～95、193 行｜D1 自增與單機 SQLite 測試不能保證整體一致**：同時同步、家長加值、cron 更新告警時，分開的讀取與寫入可能互相覆蓋、重複通知或倒退 `acked_seq`；模擬 D1 的測試也未必重現遠端併發。｜將相依更新放入適當原子操作，游標只允許前進，並增加真 D1 併發驗收；D1 `batch` 的交易語義以官方文件為準。([d1-custom-bindings-docs.previews.developers.cloudflare.com](https://d1-custom-bindings-docs.previews.developers.cloudflare.com/d1/worker-api/d1-database/?utm_source=openai))

20. **中｜第 50、52～54、71、216 行｜故障時的狀態規則互相矛盾**：狀態檔壞掉說偏向鎖，但設定檔不存在又不控管；adb 查詢失敗時不動手，YouTube 若當下開著就繼續開放。｜分別定義狀態檔、設定檔、adb 查詢失敗時的實際行為與告警，不要統稱「偏向鎖」。

21. **中｜第 94、198、255 行｜「今天扣了幾分」與校準會誤判**：當天第一筆回報前的使用量被當基準扣掉；跨午夜、離線、重裝或影子額度歸零時，v5 數字不等於 v4 的前景時間。｜標示統計起點及離線限制；校準用已知起訖的實測片段，寫清楚「≤5 分或 ≤10%」的比較基準。

22. **中｜第 243、253、265～268 行｜實機驗收可能假 PASS**：測試用 `last_seq:null` 的 curl 會先建立電視紀錄，後續首次上線可能被誤報為重裝；拔插頭的「少扣 ≤1 分」沒有量測方法；清資料後 KICK 不會恢復被清掉的金鑰與設定。｜使用隔離資料或事後清理測試紀錄；寫死測量起點、預期值及完整復原步驟。
