1. **問題：協定版本、封包大小與 checksum 沒有訂明。**  
   **為什麼：** CNXN 的版本與 maxdata 會影響雙方協商後的封包行為；測試只說驗證 checksum，卻沒有指定客戶端實際使用的版本及分段規則，實作可能通過假伺服器卻無法與真機互通。  
   **建議：** 實驗先固定使用傳統版本 `0x01000000`、maxdata `4096`，依協商結果限制傳送大小並驗證封包長度、magic 與 checksum。測試加入大於單一封包及截斷封包的情境。

2. **問題：RSA 公鑰格式與簽章方向大致正確，但驗收仍有空隙。**  
   **為什麼：** 2048 位元 mincrypt 結構的 `len=64`、`n0inv`、小端序 `n` 和 `rr`、exponent，以及對既有 20-byte token 加 SHA-1 DigestInfo 後做 PKCS#1 v1.5，都是合理假設。若直接用 `SHA1withRSA` 對 token 簽章，會再雜湊一次，結果不符。測試若只解出 `n`、`e`，仍可能漏掉結構總長、欄位偏移、小端序、Base64、註解及結尾 NUL 的錯誤。  
   **建議：** 指定結構為固定 524 bytes，逐欄檢查長度、偏移與小端序，並檢查 Base64 解碼結果和結尾 NUL；簽章測試要明確使用原始 token 驗證，避免二次 SHA-1。

3. **問題：假 adbd 的第一輪認證流程描述不夠精確。**  
   **為什麼：** 伺服器拒絕簽章後會再次送 AUTH token；客戶端送公鑰後須等待使用者授權，不能把送出公鑰直接當成認證成功。計畫也沒有規定等待授權的逾時與取消行為。  
   **建議：** 假伺服器逐步檢查 `AUTH TOKEN → SIGNATURE → AUTH TOKEN → RSAPUBLICKEY → CNXN`，第二輪檢查既有金鑰簽章成功；另測授權逾時、拒絕或斷線。將一般 I/O 逾時與等待人工授權的較長逾時分開。

4. **問題：Android 11 的 A_STLS 與本機 TCP 可用性未列為明確分支。**  
   **為什麼：** 傳統 `adb tcpip` 與 Android 11 的無線偵錯配對是不同路徑；不能只憑 API 30 判定廠商 adbd 一定接受本機傳統 TCP，或斷言所有裝置都不會要求 TLS。  
   **建議：** 保持傳統 TCP 為實驗假設；若收到 `A_STLS`，明確記錄「此端點要求 TLS，實驗不支援」並停止，不要擴寫配對或 TLS。連不上、認證失敗、要求 TLS 應分別記錄，避免一律歸咎協定實作。

5. **問題：第一次自我測試的 RSA 提示順序可能讓測試先逾時。**  
   **為什麼：** 服務心跳與自我測試都可能同時發起首次連線、觸發授權；廣播接收器的生命週期也不能靠普通背景執行緒保證。未獲授權前就依序執行測試，容易出現重複提示或測試中斷。  
   **建議：** 首次啟動先由服務建立**單一**連線並等待 Owner 勾選允許，確認 `echo ok` 後才觸發自我測試。接收器只負責啟動服務，測試由服務執行；明定等待提示的逾時與失敗紀錄。

6. **問題：Mac 驗證不一定能產生計畫預期的提示。**  
   **為什麼：** Docker 連到電視要使用獨立測試金鑰，否則沿用已授權的 Mac 金鑰可能不出提示；不勾「一律允許」也不應被當作重連後仍獲授權的保證。Docker 網路、使用者未及時操作或裝置授權狀態都可能造成失敗，不能直接判定是協定問題。  
   **建議：** 指定獨立、臨時的 Docker 金鑰，記錄連線階段及錯誤；只有取得足夠證據才退回協定修正。之後的電視 App 必須使用另一把自己的金鑰。

7. **問題：前景服務與開機自啟的先決條件不足。**  
   **為什麼：** API 30 可由 `BOOT_COMPLETED` 接收器啟動前景服務，但仍需宣告相應權限、及時呼叫 `startForeground()`，並考慮廠商背景管理。新安裝或被強制停止的套件可能處於 stopped 狀態；冷開機後使用者儲存空間是否已解鎖也會影響一般 `BOOT_COMPLETED` 與私有金鑰讀取。沒有桌面入口不代表安裝後一定已啟動過。  
   **建議：** 明列 Manifest 的 `INTERNET`、`RECEIVE_BOOT_COMPLETED`、`FOREGROUND_SERVICE` 權限與元件 exported 設定，及啟動服務後立即升為前景的要求。驗收前先以明確廣播啟動一次；分別記錄是否曾強制停止、開機後是否需解鎖，以及通知是否存在。

8. **問題：`run-as` 可行，但私鑰暴露與備份風險未納入。**  
   **為什麼：** `debuggable=true` 通常可讓 shell 使用 `run-as` 讀取該 App 私有資料，但仍取決於裝置設定；同樣也可能讀到 adb 私鑰。此金鑰具備電視 shell 權限。  
   **建議：** 明確設定 `android:allowBackup="false"`，驗證真機 `run-as`，不要把私鑰印到紀錄或報告。實驗結束後移除 App，並處理留下的授權。

9. **問題：收尾的「撤銷 RSA 授權」可能影響已上線的 v4。**  
   **為什麼：** 開發者選項的撤銷 USB 偵錯授權可能清除**所有**已授權 adb 金鑰，包括 Mac 的 v4 金鑰；卸載 App 也不等於移除 adbd 端留下的公鑰。  
   **建議：** 不把全面撤銷列為預設收尾。先確認裝置是否有可只移除實驗金鑰的方法；若只能全面撤銷，應先準備 Mac 重新授權與 v4 恢復步驟，再由 Owner 決定時機。

10. **問題：自我測試仍會暫時影響真實使用，失敗時未必能復原。**  
    **為什麼：** `tkey` 的 Manifest 顯示它處理 TCL T 鍵；測試停用期間 T 鍵會受影響。若 adbd 中斷、App 被殺或電視斷電，即使有 `finally`，也無法保證執行 `pm enable`。若 tkey 原本就被停用，無條件啟用也會改變原狀。  
    **建議：** 測試前確認 tkey 已啟用，並準備可從 Mac 執行的明確復原步驟。每步驗證 shell 結果及實際套件狀態；失敗時記錄復原是否成功。安排短暫 T 鍵中斷的時段，並在測後驗證 v4 與 T 鍵。

11. **問題：`grep` 和假 adbd 容易形成假通過。**  
    **為什麼：** 同一工人同時寫客戶端與測試，可能把同一個格式誤解寫進兩邊；搜尋 `disable-user` 或 `youtube` 也無法證明執行命令的目標受到限制，例如命令可由字串拼接或透過通用 CLI 傳入。  
    **建議：** 審定者獨立檢查封包測試及實際程式，加入固定的公鑰／簽章測試向量與錯誤案例。檢查所有 shell 命令的呼叫路徑；明確區分供 Docker 使用的通用測試入口與電視端可觸發的命令，確保後者只操作 tkey。

12. **問題：24 小時驗收沒有明確判定門檻，且紀錄輪替可能破壞證據。**  
    **為什麼：** 「會不會被系統砍掉」不能只看有無心跳：程序重啟、待機、服務重啟及 adbd 失敗是不同事件；`adb=ok` 也應代表輸出確實為 `ok`。按位元組保留檔案後半可能截斷一行或多位元組文字。  
    **建議：** 先訂明觀察起訖時間、允許的清醒時段心跳間隔、重啟如何計數，以及 PSS 的採樣時點；待機另列結果。記錄時保留完整行，並確認 24 小時期間證據未被輪替掉。

13. **問題：部分實驗設計可再縮小。**  
    **為什麼：** 此階段要驗證可行性，通用 shell CLI、複雜的服務重啟原因分類，以及 1 MB 日誌裁切都會增加失敗點；前提是仍能完成 Mac 協定驗證、真機自測與 24 小時觀察。  
    **建議：** 保留純 Java 客戶端及必要的 Docker 測試入口；電視端只提供固定測試命令。日誌先採足以容納實驗期間紀錄的簡單方案，重啟原因只記能可靠辨識的資訊。

未查閱指定清單外的資料，也未連網或執行 adb；協定與系統行為仍需依修正後的離線測試及真機實驗確認。
