**C-01｜統計段落缺少「結束」的保底機制，而一個永久打開的段落會污染每一天**

- **問題**：推算規則只用 ACTIVITY_RESUMED、SCREEN_NON_INTERACTIVE、DEVICE_SHUTDOWN 當作段落終止。但實際有三個終止缺口：①切到 HDMI 時，Android 端的 activity 狀態不變、螢幕仍是 INTERACTIVE，也不會有任何事件 → 最後一個 YouTube 段落會一路算到「現在」；②電視拔電或當機沒有 DEVICE_SHUTDOWN；③我們自己的 force-stop 在 HDMI/待機情境下不一定會帶出桌面 RESUMED。而 events 表「只增不刪」，一個沒有收尾的 resume 會永遠留在 DB 裡，往後每一天的查詢都把它延伸到當天 → 單日數字可以無限膨脹，而且無法從網頁修正。
- **為什麼重要**：這是唯一會產生「數字完全不可信、且 Owner 無法察覺」的失效模式；你的樣本裡 3 次關機都剛好有 DEVICE_SHUTDOWN，讓人誤以為收尾可靠（23:35:45 那次確實是 shutdown 收的尾）。樣本裡完全沒有 HDMI 切換可佐證。
- **建議改法**：①每段加保底上限（例：同一段超過 4 小時即截斷，並在頁面標「推估」）；②段落起點若早於「最後一次成功抓取 − 30 分」就不再延伸到現在（你已有 last_fetch 上限，但要明講套用到週/月每日分桶）；③DEVICE_STARTUP 一律視為邊界；④WO-T4 一定要實機做一次「YouTube → 切 HDMI → 30 分鐘 → 切回」並對照數字。
- **嚴重度**：高

**C-02｜排程在 Mac 睡著時不執行，而 07:40 正好是最可能睡著的情境**

- **問題**：設計寫「Mac 當下睡著或服務沒跑就跳過，不補做」。last_check 只放記憶體，重啟即遺失。WO-T4 的驗收是「新增 2 分鐘後的排程」——那是 Owner 盯著螢幕、Mac 一定醒著，剛好繞過唯一的真實情境（隔夜後 07:40）。
- **為什麼重要**：功能上線後可能連續數週「看起來有在跑」（log 沒有錯誤）卻從未真正切斷；Owner 只會在事後發現孩子早上照看。
- **建議改法**：①last_check 存進 state.json；②觸發條件加時間窗：`prev < target <= now` 且 `now - target <= 600 秒`；③超出窗口不要靜默跳過，寫一筆 `schedule skipped`（可被看見）；④醒來/啟動時對「已超出窗口」的規則做一次補判：只有當 log 最後一筆 `open` 時間早於規則時間才補切（代表那份授權本來就該被 07:40 清掉），否則不動。⑤WO-T4 加兩個情境：闔蓋跨 07:40、不闔蓋跨 07:40。
- **嚴重度**：高

**C-03｜排程切斷會被 v3 的「睡前強制開放」與「回家寬限」抵銷（PLAN 內部矛盾）**

- **問題（合成排程時間）**：v4 說「v3 規則不變」，但 v3 有兩條會直接反轉排程結果：(a) sleephook 收到 `sleep` → `apply(forced_open=True)` 無視授權直接啟用 YouTube；(b) 電視離線 ≥2 分鐘後重連 → `arrival()` 在無授權但前景是 YouTube 時進入寬限、不切。合成例：06:50 切斷 → 06:55 家長闔蓋 → YouTube 立刻被重新啟用且 Mac 睡了整天；或 06:50 電視離線導致切斷失敗 → 08:00 開電視看 YouTube → 重連走寬限 → 可以一路看。v3 的失效表（「Mac 睡著＝盡力開放」）在 v4 下已經與排程需求互斥，但 v4 沒有改它。
- **為什麼重要**：這是「排程」這個功能的核心承諾被系統自己推翻，且兩條路徑都是日常會發生的，不是邊角。
- **建議改法**：state.json 增加 `hard_lock`（= 最後一次排程切斷的時間）：設定時「睡前強制開放」一律不執行、`arrival()` 一律不進寬限，只有 `/open` 能清除。並在 v4 明確覆寫 v3 失效表的兩列（寫清楚「排程切斷後，Mac 睡前不再開放」）。WO-T3 要加兩個測試：切斷後送假 hook `sleep` → 不得出現 enable；切斷後送 `wake` 且前景是 YouTube → 不得進寬限。
- **嚴重度**：高

**C-04｜統計的完成標準可假通過，而且 WO 自帶的例子與自己的演算法矛盾**

- **問題**：①「真實樣本能解析、所有分鐘數 ≥ 0」——解析器回傳空清單也 100% 通過；②計算函式若不吃注入的 `now`/`last_fetch`，跨午夜與「算到現在」的測試只能靠真實時鐘，工人會寫成寬鬆斷言；③範例資料「YouTube 10:00–10:30、Netflix 10:30–10:45、10:50 螢幕關」在你自己定的規則下 Netflix 是 **20 分鐘**（10:30→10:50），不是 15——WO 沒寫期望值，工人可以反過來改期望值讓測試過。
- **為什麼重要**：使用時間是唯一「家長會拿去跟孩子對質」的數字，測試卻是整份 WO 最弱的一環。
- **建議改法**：①簽章固定為 `calc(events, now, last_fetch)`，純函式、不吃系統時鐘；②WO 直接寫死期望值（含取整規則：以秒計算、最後向下取整到分鐘）；③用真實樣本當精確斷言，我已算過：**10-30 當天 YouTube = 1753 秒（29 分 13 秒）、Netflix = 0**；若測試把視窗起點定義為樣本第一筆（22:37:03），則全樣本 YouTube 2976 秒、Netflix 1761 秒（注意樣本只從 22:37 開始，不是完整 24 小時，不要拿它 assert 整日以外的量）；④再加一條：同秒多個 RESUMED（樣本 22:43:06 有 ShellActivity＋MainActivity）不得造成重複計算。
- **嚴重度**：高

**C-05｜sqlite 在多執行緒 HTTP 下的執行緒模型完全沒定義**

- **問題**：`ThreadingHTTPServer` 每個請求一條執行緒；PLAN 只寫「sqlite3 標準庫、表 log/events/schedule」，沒有說連線怎麼拿。標準庫預設 `check_same_thread=True`：共用一條全域連線 → 第二個請求直接 ProgrammingError（500）；改成 `check_same_thread=False` 又會與背景抓取執行緒互撞 → `database is locked`。另外 PLAN 沒說「紀錄寫入失敗時的控制流」——v3 是「寫檔失敗 → 不啟用」，若照抄到 DB，DB 壞掉就等於整個門鎖壞掉。
- **為什麼重要**：症狀是隨機 500、看起來像電視壞了，而且測試序列化執行時完全看不到。
- **建議改法**：①每個請求開一條短連線（`sqlite3.connect(path, timeout=5)`）+ `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000`；②寫入集中在一條 `threading.Lock`；③建表用 `CREATE TABLE IF NOT EXISTS` 並設 `PRAGMA user_version=1`；④明訂「紀錄寫入失敗只寫文字 log，不影響 /open /lock /status」；⑤DB 檔損壞時服務照常啟動（控制狀態仍在 state.json）。測試加一條併發：同時打 `/usage` 與 `/open` ×20 次，不得出現 500。
- **嚴重度**：高

**C-06｜使用量抓取若走現有 adb 通道會拖慢鎖定，還會誤觸「回家寬限」**

- **問題**：`apply()` 持有 `adb_lock`；`read_tv()` 失敗會設 `failed_since`，而 `failed_since ≥ 120 秒` 後重連成功就呼叫 `arrival()`（＝可能進入寬限、不切斷）。若把 `dumpsys usagestats` 併進同一條通道（最省事的寫法），會有兩個後果：電視待機時抓取失敗被誤記成「電視離線」，之後「恢復」就送孩子一次寬限；抓取卡住時（兩次 8 秒）`/open` 的 19 秒期限被吃掉，回 `ok:false` 但電視其實開了。
- **為什麼重要**：把唯讀的統計功能牽連到唯一的安全機制上，是最容易被審查漏掉的耦合。
- **建議改法**：使用量抓取用獨立鎖、獨立函式，**不得**呼叫 `read_tv()`/不得寫 `failed_since`；`/usage` 只讀 DB 絕不碰 adb；`/open` 的 deadline 與抓取互不影響。測試：假 adb 的 usagestats 卡 10 秒，期間 `/open` 仍須在 20 秒內成功。
- **嚴重度**：中

**C-07｜`--links` 會印出錯的 port**

- **問題**：`gate.py` 的預設是 `TVGATE_PORT=8765`，正式 8790 只存在 plist 裡；WO-T3 明文禁止改 plist。Owner 在終端機手動跑 `python3 gate.py --links`（沒有 plist 的環境變數）就會印出 `:8765` 的連結——而 8765 正好被 Hermes 佔用。手機存下的會是失效連結，且 WO-T4 才發現。
- **為什麼重要**：這是「照文件做卻拿到壞連結」的典型，且錯誤會被當成網路問題查很久。
- **建議改法**：`--links` 支援 `--port`，預設值改成 8790（或把預設與 plist 對齊並在 README 註明）；同時印出 mDNS 版與 IP 版兩行（`ipconfig getifaddr en0`），IP 版當備援；README 加一行驗證指令 `curl -s http://<host>:8790/ | head -3`。
- **嚴重度**：中

**C-08｜「前景時間」不等於「觀看時間」，而頁面沒有揭露可信度**

- **問題**：孩子在 YouTube 上按暫停或開著去做別的事，仍算滿額；YouTube 停用期間、HDMI、待機看起來都對，但抓取有缺口時（Mac 睡著 >24h）數字會少算，PLAN 只在頁面「註明」一次；「本月」在 v4 上線前的資料根本不存在，第一天就顯示接近 24 小時的量，Owner 會以為系統已經有歷史。
- **為什麼重要**：這個數字一旦被當成「證據」使用，任何語意落差都會變成親子衝突時的可信度問題。
- **建議改法**：頁面固定顯示三行：「今日」「資料起點 YYYY-MM-DD HH:MM」「最近一次抓取 HH:MM（缺口中）」，並把分頁標題改成「前景時間」而非「使用時間」；月報只給總計並加註「含未抓取時段不計」。
- **嚴重度**：中

**C-09｜鑰匙放 localStorage 是脆弱設計，可以直接刪掉**

- **問題**：`#t=` 存進 localStorage 再清 hash，多出「清 hash」「沒有鑰匙時顯示提示」「三台裝置各自不同狀態」的邏輯，還要面對 iOS Safari 對 7 天未互動網站的 script-writable storage 清理。但 iPhone「加到主畫面」與 Safari 書籤本身就會保存完整 URL（含 `#` 片段），而片段不會送到伺服器，安全性沒有損失。
- **為什麼重要**：這是典型的「多寫 30 行換一個新失效模式」——某天早上打開主畫面，發現要重新傳連結。
- **建議改法**：頁面每次載入直接讀 `location.hash` 取 token；不寫 localStorage、不清 hash、不做鑰匙持久化。token 遺失就是「請用裝置連結開啟」，一行提示即可。這一條同時是「可刪」清單的第一項。
- **嚴重度**：中

**C-10｜鑰匙檔的錯誤處理與輪替流程沒寫**

- **問題**：每個請求都 `json.loads(tokens.json)`；檔案損壞、權限錯、內容不是 dict、值是數字 → 若未攔截就是 500（甚至整條執行緒例外），而不是 401。另外「連結洩漏怎麼辦」在 v4 完全沒提：改檔案後是否免重啟生效？舊連結是否立刻失效？
- **為什麼重要**：三把萬用鑰匙且永久有效，是這個系統最高的單點風險；沒有輪替程序，出事時 Owner 只能全部重來。
- **建議改法**：讀檔失敗一律 401、並在文字 log 記一行（不要區分「檔案壞」與「鑰匙錯」給外部）；README 寫 3 步輪替：改 `tvgate.tokens.json`（刪掉舊那把）→ 重跑 `--links` → 重新傳連結，並註明「不需重啟服務」。WO-T4 加一項實測：刪掉一把 → 舊連結 401、其他兩把正常。
- **嚴重度**：中

**C-11｜紀錄雙軌不要合併，舊 action 名稱不要改**

- **問題**：PLAN 用 DB 表 `log` 取代既有文字 log，並把 `apply` 改名為 `manual-relock`、新增 `expire`/`away`/`grace`/`schedule`。既有 14 個測試與 v3 失效表都對應舊名稱；文字 log 又是「服務整個掛掉、DB 也沒寫進去」時唯一的現場證據。
- **為什麼重要**：改名只是為了網頁好看，代價是工人要改既有測試（最容易在這裡偷偷放寬斷言），而 debug 能力反而下降。
- **建議改法**：`log()` 維持一個函式、同時寫文字 log 與 DB（同一份內容兩個 sink）；既有 action 名稱不動，只**新增** `schedule`；`device` 欄位只加在 open/lock 與系統事件。並明訂「DB 寫入失敗不影響文字 log 與控制流」。
- **嚴重度**：中

**C-12｜測試隔離有漏洞，而且 `now` 與 last_check 的介面沒定義**

- **問題**：`LOG` 寫死在 `Path.home()/Library/Logs/tvgate.log`，完全不理 `TVGATE_HOME`——現在每一輪測試都往真機 log 寫；WO-T3 禁止碰 `~/.secrets` 與 `~/Library/Application Support/tvgate`，但這條路徑是漏的，而 `git status` 檢查抓不到（在 repo 外）。另外排程判斷函式只寫「輸入規則、上次檢查時間、現在」，沒說 last_check 是否持久化、何時更新（若在慢速 apply 之後才讀時鐘，跨過規則時間的區間會被吃掉）。
- **建議改法**：①log 路徑改 `$TVGATE_HOME/tvgate.log`（可用 `TVGATE_LOG` 覆寫），並在測試裡斷言「跑完後 `~/Library/Logs/tvgate.log` 的 mtime 不變」；②判斷函式簽章 `schedule_due(rules, prev, now) -> [(rule, target)]`，`prev` 由呼叫端先取一次 `now`、先推進 `prev` 再做切斷（避免重複/漏做）；③`days` 要用 **target 的日期** 判斷週幾，不是 `now` 的日期（否則 23:59 的規則在次日 00:00:02 檢查時會用錯星期）。
- **嚴重度**：中

**C-13｜WO-T3 測試清單缺的可執行項**

- **問題**：現有清單缺：併發（見 C-05）、tokens.json 壞檔/缺檔 → 401 且不是 500、`/schedule/add` 的邊界（非 JSON、缺 Content-Type、Content-Length 缺或過大、`time="7:40"`、`days` 有重複或字串、重複規則）、`/usage` 在 DB 不存在或空表 → 200 空資料不是 500、`GET /` 必須 200 且帶 `Cache-Control: no-store`、`HEAD /` 不得回 body、dumpsys 的「段落結束」判定（必須以「下一個 section 標題或 EOF」為界，樣本前 80 行全是 STANDBY_BUCKET_CHANGED 與 3 個 `UNKNOWN_TYPE_`，不可因未知 type 報錯或誤判段落結束）、以及「排程切斷與手動 `/open` 同秒競態時兩筆紀錄都要留下」。
- **為什麼重要**：這些都是工人會「順手用 try/except 吞掉」的地方；吞掉之後測試仍全綠。
- **建議改法**：把上面每一項直接寫成 WO-T3 的條列驗收；並加一條反向檢查：故意把解析器改成「只認 YouTube」或「忽略 SCREEN_NON_INTERACTIVE」，對應測試必須失敗（抽 1 條做 mutation 檢查，成本很低）。
- **嚴重度**：中

**C-14｜WO-T4 驗收缺的東西**

- **問題**：①「使用時間今天有數字且與 Owner 印象相符」不可驗證、必過；②沒有「Mac 睡著跨 07:40」（C-02）；③沒有「排程切斷後闔蓋／之後電視重連」（C-03）；④沒有播放中被切斷後 30 分鐘的數字（驗 force-stop 是否留下沒收尾的段落，C-01）；⑤沒有 HDMI 切換、待機、YouTube 停用期間的對照；⑥沒有還原程序（v3 WO-T2 有，v4 沒有）；⑦沒有清掉 v3 那 5 個 iPhone 捷徑（新格式後它們會 401，Owner 會誤按）；⑧沒有防火牆/8790 與「8765 仍是 Hermes」的確認；⑨沒有鑰匙輪替實測（C-10）。
- **建議改法**：把 ①改成可量測：Owner 現場記錄 3 次「開始/結束」時間，與 `/usage` 對照，誤差 ≤ 5 分鐘算過，並寫進驗收表；②③④各指定一次實機腳本與預期（②：闔蓋跨 07:40，醒來後紀錄須有 `schedule` 或 `schedule skipped`；④：切斷後靜置 30 分鐘，YouTube 當日分鐘數不得增加）。⑧⑨與還原程序寫進 README 並在 WO-T4 逐項打勾。
- **嚴重度**：中

**C-15｜過度設計，可刪的部分**

- **問題**：「本週、本月另回每天的分鐘數」——手機上 31 列 × 6 條橫條；`index.html` 另存一個檔（多一個路徑、`git status` 檢查變複雜）；`/log?limit` 可調到 200；以及未明訂「不做」的清單（DB 清理、事件重算、月份切換、跨裝置同步）。
- **建議改法**：①HTML/CSS/JS 全部內嵌 `gate.py`（少一個檔、少一類 base-path 錯誤）；②month 只回總計，week 才給每日；③`/log` 固定最近 30 筆（除錯時直接看文字 log）；④在「不做」補一行：不做歷史資料修正/清理、不做事後重算、排程上限 20 條（超過 400）。這些刪掉不影響任何驗收項。
