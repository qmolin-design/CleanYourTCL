1. **C-01｜睡眠通知不能保證留有足夠時間開放 YouTube**
   - **問題：**計畫假設 `willSleepNotification` 的 handler 等到 Python 回覆，就能讓 Mac 等待 ADB 完成；文件沒有證據支持這個時序。
   - **為什麼重要：**ADB 每次最多等 10 秒，還可能重連和重試；Mac 可能先睡著，YouTube 留在鎖定狀態。
   - **建議改法：**把「睡前先開放」改成**盡力而為、待實機驗證**，不要宣稱保證成功；先驗證通知送達、網路仍可用、指令完成與實際入睡的先後。若無法可靠達成，回報 Owner 決定是否接受。
   - **嚴重度：高**

2. **C-02｜休眠時電視離線，無法兌現「Mac 不在就開放」**
   - **問題：**Mac 要睡時，電視可能待機、斷網或尚未接受 ADB，服務無法改變電視狀態。
   - **為什麼重要：**若 YouTube 當時已鎖，Mac 睡後也不能補送指令，家人可能一直無法看；這與 Owner 的目標直接衝突。
   - **建議改法：**失效表明列此限制；T2 實測「鎖定中電視待機／斷網，Mac 再睡」。若不能接受，需先決定替代操作方式，不能靠軟體保證離線電視變更狀態。
   - **嚴重度：高**

3. **C-03｜關機、登出和服務停止不等於一定能完成 SIGTERM 清理**
   - **問題：**收到 SIGTERM 不代表程序一定有時間完成重連與啟用；非正常終止可能完全收不到，正常停止也可能被限時結束。
   - **為什麼重要：**失效表目前把關機寫成必然先開放，容易讓家人以為服務停止後一定能看。
   - **建議改法：**明列「成功執行清理時才開放」，將逾時、網路不可用、程序被強制結束列為可能維持最後狀態；T2 分別測登出、正常關機及手動停服務。
   - **嚴重度：高**

4. **C-04｜`KeepAlive` 與「停止即開放」可能互相打架**
   - **問題：**服務意外退出後，launchd 可能重啟；重啟後若無有效授權，服務又會鎖回。`kickstart -k` 也可能先觸發清理再重啟。
   - **為什麼重要：**「服務停止＝開放」不是穩定結果，重啟期間還可能短暫開放或打斷播放。
   - **建議改法：**區分「永久停用服務」與「程序被重啟」的預期；T2 實測 `kickstart -k`、`bootout` 和意外退出，記錄最終狀態及到期時間，不以到期時間未變作為唯一通過條件。
   - **嚴重度：高**

5. **C-05｜電視重開後改回啟用，未必發生在 ADB 重連之前**
   - **問題：**實機只證明一次重開後最後變成啟用，沒有證明開機程序改狀態必定早於 ADB 可連。若先連上並對帳，之後系統才啟用，仍要等下一輪。
   - **為什麼重要：**「重連立即對帳」不足以保證立刻鎖回，也不能由單次 50 秒推導每次 1～2 分鐘。
   - **建議改法：**保留定期對帳作補救，實測多次冷重開及待機喚醒，記錄 ADB 可用、YouTube 被啟用、再次停用的時間；承諾只寫實測支持的範圍。
   - **嚴重度：高**

6. **C-06｜「最多 60 秒」沒有計入命令耗時與排隊**
   - **問題：**60 秒對帳間隔之外，還有迴圈排程、鎖等待、ADB 逾時、重連和重試；串行處理時可能更久。
   - **為什麼重要：**Owner 接受的是手動啟用後 60 秒內停回，目前規格沒有證明能達成。
   - **建議改法：**明定在線且 ADB 正常時，從按啟用到實際停用的上限；用真實最壞情境驗證，調整週期及逾時以符合 60 秒。離線或 ADB 故障另列例外。
   - **嚴重度：高**

7. **C-07｜ADB「指令失敗」的定義不足**
   - **問題：**只看 subprocess 退出碼未必足以判定電視端操作成功；`adb connect` 也需要確認目標真正可用。多台裝置時若未指定目標，命令可能失敗或送錯裝置。
   - **為什麼重要：**服務可能回報成功，實際卻沒改到指定電視。
   - **建議改法：**每個裝置命令明確指定目標；檢查逾時、退出碼及必要輸出，變更後讀回狀態。重連失敗時回報離線或具體錯誤，不把命令已送出視為成功。
   - **嚴重度：高**

8. **C-08｜只查停用清單，不能把「查不到」直接當啟用**
   - **問題：**YouTube 不在 `pm list packages -d` 結果中，也可能是查詢失敗、輸出異常、套件不存在或使用者不符；子字串匹配還可能誤認 `youtube.tvmusic`。
   - **為什麼重要：**可能誤報開放成功，或漏掉該停用的套件。
   - **建議改法：**明確針對 user 0 和完整套件名稱解析；查詢失敗或無法判定時標為未知／離線，不回成功。測試包含相似套件名、空輸出和命令失敗。
   - **嚴重度：高**

9. **C-09｜到期與立即鎖的優先權沒有落實**
   - **問題：**同一把鎖只保證互斥，不保證「立即鎖優先」；慢速 `/open`、對帳或 sleep 處理可能先佔住鎖。原方案已裁定立即鎖優先。
   - **為什麼重要：**家長按鎖或時間到後，可能等多次 ADB 逾時才執行；先前的開放動作也可能覆蓋較新的鎖定意圖。
   - **建議改法：**明確定義請求先後及優先規則，至少確保較舊動作不能在較新鎖定後重新開放；加入慢速 ADB 下的並發與到期測試，量測最長等待。
   - **嚴重度：高**

10. **C-10｜Python 標準庫 HTTP 的阻塞與錯誤處理未定**
    - **問題：**標準庫能實作 HTTP，但若用單執行緒伺服器，慢請求或慢 ADB 可能讓其他請求排隊；若使用多執行緒，則必須正確處理共用狀態。請求格式、方法與逾時也未規定。
    - **為什麼重要：**一個卡住的連線可能讓 iPhone 查不到狀態或按鎖無反應，甚至影響 60 秒目標。
    - **建議改法：**選擇最小可行的並行處理方式並設連線逾時；明定錯誤方法、未知路徑、缺少／重複／非法 `min` 的回應。測試慢連線時其他請求仍可完成。
    - **嚴重度：中**

11. **C-11｜狀態可能把「應該」誤當「實際」**
    - **問題：**`allowed` 是授權意圖，`tv` 是電視實際狀態；`last_check` 沒說是嘗試時間還是成功讀取時間，且 `tv` 沒有未知狀態。
    - **為什麼重要：**例如 `/open` 失敗但到期時間仍記錄時，`allowed=true` 不代表電視可看；舊的成功結果也可能被誤認為現在狀態。
    - **建議改法：**明確定義欄位：授權是否有效、最後一次**成功**讀取的實際狀態及時間；無法確認時顯示離線／未知。捷徑用清楚文字區分「已授權」和「電視已開放」。
    - **嚴重度：中**

12. **C-12｜啟用失敗仍保留授權，可能稍後自行開放**
    - **問題：**`/open` 先記到期時間，失敗後對帳若恢復連線，仍可能啟用 YouTube，即使家長剛看到失敗。
    - **為什麼重要：**這符合倒數照記的既有規則，但對 Owner 的操作感受不直觀：失敗不代表後續不會開放。
    - **建議改法：**保留既定規則，但失敗訊息明示「授權仍有效至何時，恢復連線後可能自動開放」；加測此行為和 `/lock` 能取消它。
    - **嚴重度：中**

13. **C-13｜安全寫入只涵蓋一半，寫入失敗未定義**
    - **問題：**原子取代可避免看到半份檔案，但目錄不存在、權限不足或磁碟寫入失敗時，計畫沒說是否仍執行啟用／停用或如何回覆。
    - **為什麼重要：**記憶體狀態、磁碟狀態和電視可能互相矛盾；重啟後可能恢復舊授權。
    - **建議改法：**明定持久化失敗時不得回報成功，並定義鎖定與開放各自如何處理；測目錄不可寫及重啟後結果。損壞檔案視為未授權也要留可辨識的錯誤紀錄。
    - **嚴重度：高**

14. **C-14｜刪除未校時規則需要承認代價**
    - **問題：**「Mac 一直有網路校時」不等於時鐘絕不錯或不會跳動；用絕對時間判斷授權會受系統時間影響。
    - **為什麼重要：**時間跳快可能提前鎖，跳慢可能延長觀看。
    - **建議改法：**不必因此建立完整校時監控，但應在失效表寫出時鐘錯誤的後果，並測一次時間變動或以可控時鐘測試到期判斷。
    - **嚴重度：中**

15. **C-15｜sleephook 與啟動組態有額外故障點，應先證明必要**
    - **問題：**新增 Swift 子程序、雙向管線、編譯與 launchd，帶來子程序退出、管線斷線、回覆永遠等不到及重啟清理等問題；「約 20 行」不能證明低維護。
    - **為什麼重要：**這些複雜度是為睡前開放而加，但 C-01、C-02 尚未證明它足以達成目標。
    - **建議改法：**先做一次最小實機時序驗證，再決定保留 hook；協定至少要有超時及子程序失效時的可見錯誤。若 Owner 接受睡前手動開放，則可刪掉整個 hook，但須先取得該裁定。
    - **嚴重度：中**

16. **C-16｜WO-T1 可用假測試或不完整檔案「通過」**
    - **問題：**`exit 0` 無法證明測試真的起 HTTP、使用產生的假 adb、驗證指令順序或讀回狀態；`git diff --stat` 也可能漏掉未追蹤的新檔。假 adb 卡住測試若仍用 10 秒上限並重試，完成時間可能遠超預期。
    - **為什麼重要：**表面全綠不代表需求已實作，甚至可能誤碰真電視或污染使用者真正的狀態檔。
    - **建議改法：**審核實際程式和測試；測試使用隔離的暫存 HOME／狀態與 token，明確禁止真 adb，驗證實際請求、完整參數、順序與最終狀態；檢查含未追蹤檔的工作目錄狀態。逾時測試明定總上限並確認程序無殘留。
    - **嚴重度：高**

17. **C-17｜WO-T1 的 sleep 測試可能沒有測到真實接線**
    - **問題：**「stdin 模擬 sleephook」未說明 stdin 屬於哪個程序、如何接到 gate.py，以及如何確認 `ok` 直到 enable **成功並讀回**後才送出。
    - **為什麼重要：**測試可能只驗證假輸入處理，實際 Swift 子程序管線卻不通，或在失敗時仍回 `ok`。
    - **建議改法：**用可控假 hook 走與正式子程序相同的管線，測成功、ADB 失敗、hook 斷線與逾時；Swift 編譯成功只算編譯檢查，不能算實際休眠驗證。
    - **嚴重度：高**

18. **C-18｜WO-T2 缺少啟動環境和日常恢復驗收**
    - **問題：**`plutil -lint` 只驗證 plist 格式，不證明登入後會啟動、路徑正確、ADB 與 Swift 程序找得到，或 iPhone 的 `.local` 名稱可解析。測試中的自訂 `ADB` 與隨機埠也不能證明正式設定可用。
    - **為什麼重要：**手動執行正常，重登入或重開 Mac 後仍可能完全失效。
    - **建議改法：**用正式安裝位置和 launchd 設定，實測登入自啟、重登入／重開機、喚醒後服務恢復、iPhone 連線及 log 記錄；同時確認 DHCP 保留和電視 ADB 授權。
    - **嚴重度：高**

19. **C-19｜WO-T2 的實機情境和回復條件不足**
    - **問題：**待機結果仍「待補」；現有驗收未明確測手動啟用的實際停回時間、播放中闔蓋、喚醒切播、電視離線時休眠，以及安裝前原始狀態。還原命令固定啟用 YouTube，未必是原始狀態。
    - **為什麼重要：**這些正是 Owner 裁定與方案最大的不確定處；固定啟用也可能改變原本設定。
    - **建議改法：**T2 補上述情境並記錄時間與結果；先記原始狀態，還原時依原狀處理、確認服務及子程序已停止。Q5「喚醒立即切播」先由 Owner 決定再驗收。
    - **嚴重度：高**

20. **C-20｜明文 token 與入口盤點要如實列風險**
    - **問題：**區網 HTTP 的 token 會隨請求以明文傳送；iPhone 投放未測，其他 App 連結及第三方播放器的結果也未在閘門紀錄中確認。
    - **為什麼重要：**token 不是防同網路側錄的保障；入口未測不能宣稱完整防繞過。
    - **建議改法：**不必為一般家庭使用先增加大型安全架構，但限制服務不對外網開放、保護 token 檔案，並讓 Owner 知道區網明文風險。T2 逐項填入口結果；家中不用投放可記「未測、Owner 接受」，不可記成已擋住。
    - **嚴重度：中**
